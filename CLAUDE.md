# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

This is `backend` (module `github.com/Raccoon-CI/backend`): the server of Raccoon CI, a self-hosted CI/CD platform that moves workflows from GitHub Actions onto compute the user chooses. The server receives GitHub's events, decides which workflows run, runs every job instance on a machine of a compute provider (InstaBox first), keeps the results, logs, artifacts and caches, and serves them through a JSON API. Its contract with the frontend is `internal/server/api/openapi.yaml` (served at `/v1/openapi.yaml`); a test keeps it in step with the routes.

Contents: `cmd/raccoonci-server`, `internal/server/*`, `deploy/` (Dockerfile, systemd unit, Caddyfile), `docs/` (server design, running it, deploying it, registering the GitHub App; English `x.md` plus Chinese `x.zh.md`, keep the pairs in step).

Compute providers are pluggable (the user's own machines, InstaBox, later cheap clouds); runners are Linux only for now. The config format is GitHub Actions workflow YAML and must not lose GHA features.

## Depends on

- Only `github.com/Raccoon-CI/lib` (`pkg/*`: value, workflow, expr, trigger, cron, catalog, runnerimages, wire, dispatch, runevent, jobgraph, instabox, blob, artifact, cache, archive, ...). Dependency direction: lib <- runner <- cli, and lib <- backend. **The backend must never import the runner or the cli**; `internal/server/execute/deps_test.go` runs `go list -deps -test ./...` and fails if `raccoonci-runner` or `cli` shows up.
- It does *run* the runner's binary at run time: the machine's agent (`raccoonci-runner agent` / `raccoonci run-instance`, built in the runner and cli repositories) speaks `pkg/dispatch` to this server. The `-local-runner PATH` development mode takes the path of such a binary. That is the only link, and it is a protocol (`dispatch.ProtocolVersion`), not an import.

## Developing across the repositories

`go.mod` requires the published `lib v0.1.0` (and nothing from the runner), so `go build ./... && go test ./...` work on their own, and so does CI. To try a change to lib together with this repository, put the checkouts side by side and add a `go.work` next to them with a `use` line for each directory (do not commit it). `go mod tidy` has been run against the published tag.

## Commands

```sh
make build                # builds dist/raccoonci-server (VERSION=x.y.z sets main.version)
make test                 # go test ./...
make race                 # go test -race ./...
make vet                  # go vet ./...
make check                # vet + race — must pass before merging
go test ./internal/server/store -run TestName -v   # run a single test
```

Use `GOFLAGS=-p=1` for test and build runs: the suite is heavy under `-race` and some timing tests are slow on a shared machine.

`raccoonci-server -allow owner/name [-allow …] [-listen 127.0.0.1:18080] [-data-dir DIR]` (`cmd/raccoonci-server`; plan: `docs/server-design.md`; how to run it: `docs/server-dev.md`; how to deploy it: `docs/deploy.md`). Secrets come from the environment or `NAME_FILE` (a file only the owner can read; systemd credentials in `$CREDENTIALS_DIRECTORY` are the one exception), never from flags.

## Layout

- `cmd/raccoonci-server/main.go`: wires everything; `check.go` is `-check` (container health check against `/readyz`), `perms.go` the database file and data directory permissions, `storage.go` and `replay.go` the bucket check and webhook replay helpers. `version` lives in `package main`, set with `-ldflags "-X main.version=..."` in the Makefile.
- `internal/server/<pkg>`: `api`, `artifacts`, `auth`, `caches`, `catalogsync`, `config`, `execute`, `github`, `imagesync`, `instsync`, `intake`, `oidc`, `retention`, `schedule`, `secrets`, `storage`, `storagecheck`, `store`, `vault`. Keep `main` thin.
- New binaries would need adding to the Makefile `build` target.

## Architecture

The server was written inside the monorepo under rules that made the split a move: it imports only lib packages and reaches the outside through small interfaces of its own. Below, the per-package notes (steps are those of `docs/server-design.md`; what is left of each is in TODO C.1).

- `internal/server/…`: the server (steps 1 and 2 of `docs/server-design.md`: intake and run records, then execution). Steps beyond intake: `execute` (`Executor` takes queued runs with `Store.ClaimRun`, fetches the source, runs `jobgraph.Run` with `Options.Remote`, one machine per job instance through the `Machine` interface, and stores the instances' events as the run's log through a batching `sink`; `Instabox` adapts `instabox.Provider`, `Local` runs `raccoonci run-instance` (the binary from the cli repository) on the server's own machine with no isolation (`-local-runner`, development and trusted code only); runs left in progress by a stopped server are ended as failed at start, and stopping the server cancels the ones running; `githubContext` builds the github context from the stored run), `artifacts` (the artifact service for all runs, a token scoped to one run and job; `Config.S3` keeps its data in a bucket), `caches` (the cache protocol v1 routed by space, see below), `storagecheck` (tries a bucket at start: write, read back through a presigned link, delete, and a warning when plain unauthenticated requests get the object), `github.Client.SourceTar` (GitHub's archive repacked under one top-level `src/`, which is what `archive.ExtractTarGz` on the agent expects: it drops the first path component), `intake.Handler.Dispatch` (`POST /v1/runs`: start a `workflow_dispatch` workflow by hand, inputs checked by `trigger.DispatchInputs`), and in `api` the jobs list, the log (paged, or server-sent events with `Last-Event-ID` resume) and the dispatch route; `routes()` is the one table of routes and a test checks every one is in `openapi.yaml`. A run's log is one ordered stream of JSON events (`log_lines`, kind names not numbers); a run's jobs are rows of `jobs`. Verified end to end with `-local-runner` (a real workflow of a bench repository, 62 log lines, 4 s, streamed live over the tunnel) and on an InstaBox machine from the runner snapshot `raccoonci-runner-9c482bc` through the tunnel's `/agent` (machine up in 9.8 s, run done in 16 s, machine deleted). The Secrets of the InstaBox machine (`IBX_API_KEY`) are only in login shells (`bash -lc`); the agent's Bash tool shell does not have them. The pull request commit is its head, not GitHub's merge commit; no `.git` in the source; no secrets yet.
  Step 3 (partly): `execute.Reporter` is told when a run starts (`pending`) and how it ended; `execute.Statuses` implements it as a commit status `raccoonci / <workflow name>` through `github.Client.SetStatus`, which works with a token and with an App (check runs need an App and are not done). The end report waits for the start report so a slow one cannot overwrite it; a failed report is logged only. `Executor.Cancel(runID)` cancels one run's context (the run ends as `cancelled`, machines deleted); `API` routes `POST /v1/runs/{id}/cancel` (a queued run ends at once through `Store.CancelQueued`, a running one through the `Canceller`) and `POST /v1/runs/{id}/rerun` (`intake.Handler.Rerun`: a new run with the same commit, workflow text and inputs under a new synthetic event; `rerun_of` points at the first run of the chain). `instabox.Client.DeleteMachine` waits and retries on 409 `operation_conflict` (found live: cancelling while a machine was being created left it running for the 2 h deadline). GitHub-sent deliveries (ping, push, pull request) were checked against a real repository webhook; a run from such a delivery was not, because the token has no `workflow` scope to add a push workflow.
  Step 4 (caches): `caches.Service` sits in front of one ordinary `cache.Service` per **space**, made when first needed (an index file under `<data>/caches/cache/<repo hash>/<space>/` and objects in `objects/` there or under the prefix `cache/<space>/` in the bucket, with `Dir` links under `/_cache_dl/<space>/`). `SpaceFor(repo, ref, defaultBranch)`: the default branch has the space `default`, written only by its own runs; every other ref has `r-<hash of the ref>` and reads its own then `default`; repositories are told apart by a hash of the lower-cased name. A request is routed by its token: the run id in the token goes to `Config.Spaces` (`Resolver`: the stored run's repo and ref, the repository's default branch from GitHub kept 10 minutes; without it every run is taken for a non-default one: fewer hits, never less safe), the lookup (`GET cache`) tries the spaces in order and answers 204 only if none has the key, everything else goes to the run's own space. Only v1 is advertised (`ACTIONS_CACHE_SERVICE_V2` is cleared). Expiry and the repository cap: see Cache sweep below. Checked with the real `setup-go` cache in jobs on InstaBox (save, restore on rerun, restore from a feature branch through the default space); the bucket path (S3) only against fakes. Artifact metadata: see Artifacts below.
  Step 6 (schedules, start limit): `pkg/cron` (the five-field cron parser, moved out of `ghrunner`, which keeps aliases; for the library) and `internal/server/schedule`. `Scheduler` looks every 15 s at the repositories the store has an event for (`Store.Repos`, with the newest installation id) plus those named exactly in `-allow`, keeps each one's schedule entries on the **default branch** for 5 minutes, and for an entry whose minute has come reads the workflow again at the branch's newest commit (the entry must still be there; `trigger.Match` with the `schedule` event), records an event `schedule-<repo>-<file>-<hash of cron>-<unix minute>` (a restart or a second server cannot fire it twice; `CreateRun` is idempotent per event and file) and queues the run (`github.event_name` `schedule`, `event.schedule` the cron, actor `schedule`). Missed fires are not made up; after a stall one run, not a burst. `-schedule=false` leaves it to GitHub. Unit-tested only: no benchmark repository has a `schedule:` and the token cannot add one. `instabox.StartLimit` (`Provider.Limit`, server flag `-starts-per-minute`, default 10): a sliding 62 s window of the server's own starts, a start over the limit waits; after a 429 every start waits 20 s and the refused one is asked again (at most 20 times); without a limit a 429 is still an error. Live (2026-11-02, limit 2): four runs at once, two machines up in 9–11 s and two after waiting 1 m 0.5 s and 1 m 1.5 s, all four succeeded, no machine left; a real 429 was not seen. InstaBox had no snapshots left in the account that day (the old runner snapshot was gone, every run failed with "snapshot not found"); `raccoonci runner-snapshot` rebuilt it.
  Artifacts: finished artifacts are rows of `artifacts` (migration 0006; `Store.PutArtifact/ListArtifacts/DeleteArtifact/ExpiredArtifacts`), one `scope` per artifact service (`disk`, or `<org>@<bucket version>`, ids count per scope), through `artifacts.recordIndex` as the service's `artifact.Index`. `artifacts.Service.List/DownloadURL` serve `GET /v1/runs/{id}/artifacts` and `.../{artifact}/download` (302 to a presigned link, read role); `Sweep` (hourly `Janitor`, and at start) expires through each run's service and only forgets records no current service holds (an organization's replaced bucket: its objects stay there), leaving alone those whose service could not be reached; `-artifact-retention-days` (90) is both default and cap. Uploads in progress are not remembered (multipart pieces from an interrupted one stay in the bucket). Tested with the real upload protocol against SQLite and live for the migration and the routes on the existing database; no job that uploads an artifact was run on the server (no benchmark workflow does, and the token cannot add one).
  Cache sweep (`caches/sweep.go`; `cache.Service` gained `Entries`, `ReadIndex`, `Evict`, `Expire`, `Idle`): `Sweep` (run by `Janitor` at start and every 15 minutes) lists the spaces that have an `index.json`, reads each index without opening the space (the live last-use times when it is open), and only opens a space that has an entry unused for `MaxAge` (7 days, `-cache-max-age-days`) or is empty: `Expire` deletes those entries and their objects, and a space left with nothing and no upload in progress is closed and its directory removed (`removeSpace` checks idleness again under the lock). Then `capRepos` takes each repository's entries across all its spaces and deletes the least recently used until the total is under `MaxRepoBytes` (`-cache-repo-limit-gb`, 10, 0 = none), so that cap is soft (checked per sweep), while the per-space `MaxBytes` is still checked at each upload. A space's organization (whose bucket its objects are in) is written to `<space>/org` when the space is opened, since the directory name is a hash; a space without that file is taken for a disk space if it has `objects/`, else left alone. A restore's time (`Used`) is written with the index at most every 5 minutes (`saveEvery`) and at `Close`, because it used to reach the disk only with the next commit. Live: the real `setup-go` cache restored in a job on InstaBox after the restart, its `used` reached the disk at once, the `org` file appeared and the sweep left the live space alone. Expiry and the repository cap themselves are tested (clock moved by passing `now`, mutation-checked for the cap), not seen live: the shortest age is one day and the entries were hours old. Bucket objects of an interrupted multipart upload are not swept.
  Installation of a run started by hand: `intake.Handler.installationFor(repo)` takes the newest installation id any stored event named for the repository, else asks `Handler.Installation` (`github.App.InstallationOf`: `GET /repos/{repo}/installation` with the App's JWT; `ErrNotFound` becomes a 404 "not installed"), and `Dispatch` and `Rerun` put it on the event, which is where the executor reads it. A token (no App) leaves it 0. Unit-tested; not against real GitHub (no App registered yet).
  Leftovers of a crash: `Executor.Run` calls `clean` right after `RequeueInterrupted`, which empties `WorkDir` and, if the `Machine` has `Clean() error` (`Local` does), its job directory; `artifacts.New` removes `<dir>/spool` and `caches.New` removes `<dir>/cache-spool`. Safe only because one server uses a data directory. Unit-tested; the crash case itself was not seen live. No disk quota yet.
  Log retention (`internal/server/retention`): `Janitor.Sweep` (start, then hourly) calls `Store.PurgeLogs(before, 100)` until a batch is not full: it deletes the `log_lines` of finished runs whose `updated_at` is older than `-log-retention-days` (90; float, 0 = for ever) and sets `runs.log_purged` (migration 0007), in one transaction per batch. The log routes (paged and SSE) answer 410 for such a run, `log_purged` is in the run's JSON; the run, jobs and result stay. Raw delivery payloads and workflow texts are not purged (a rerun reads them). Live on the dev database with `0.01` days: 20 runs, 766 lines purged, a 12-minute-old run kept its log.
  Restarts: a run in progress when the server stops is run again from its beginning, not resumed. `runs.attempts` (migration 0005) is bumped by `ClaimRun`; `Store.RequeueInterrupted` at start (after a crash) and `Store.Requeue` when the executor sees its parent context ended while the run was cancelled (SIGTERM; a `Cancel` by a person is not that) put the run back in the queue and delete its job rows (the log stays, plus a warning "attempt N") while `attempts < Executor.MaxAttempts` (3), else it ends as failed. A requeued run sends no end status to GitHub (it stays `pending`). Live: both paths on InstaBox (killed mid-run, and SIGTERM mid-run) ended in success on attempt 2; the machines of a crashed attempt are not known any more and expire at their deadline.
  Step 5 (secrets, roles; no GitHub login yet): `vault` seals values with AES-256-GCM under the master key (`RACCOONCI_MASTER_KEY`, 64 hex digits or base64; `-master-key-id`, and `RACCOONCI_MASTER_KEY_OLD` with `-master-key-old-id` to open what an older key sealed), binding each to its scope and name as additional data so a copied row does not open; the key id is stored with the value. `secrets.Service` keeps secrets (sealed, never read back, only listed by name) and variables (plain, listed with values) in the `secrets` table, scope `org:<name>` or `repo:<owner>/<name>` in lower case, names in capitals (GITHUB_ names refused, 100 characters, 48 KiB). `ForRun(repo, workflowText, fork)` returns what a run gets: the repository's secrets over the organization's, only those the workflow names literally (`Referenced`; `secrets[matrix.x]` and `toJSON(secrets)` do not pass anything), none for a fork's pull request (the run's log says so), variables for all. `execute.Executor.Secrets` puts them in `dispatch.Job.Secrets` (the run-instance flag `-secret NAME` and the environment, as `raccoonci run -on instabox` does) and the variables in the `vars` context; the opened values are never written to disk or the log. `api`: routes have an access level (open, read, admin; `routes()` is still the one table and the spec test covers it); the bootstrap token (`RACCOONCI_API_TOKEN`) is admin, other tokens are made with `POST /v1/tokens` and only their SHA-256 is kept (`api_tokens`); `read` reads runs, jobs, logs and events, everything that changes something and everything about secrets and tokens is admin (403 otherwise); a header without the `Bearer ` scheme is refused. Checked with the real `run-instance` (`RACCOONCI_TEST_BIN=dist/raccoonci`, `real_test.go`: the secret printed as `***`, absent from the log, empty for a fork) and live through the tunnel. Not done: a bucket per organization (the storage settings would be a secret of the organization; artifacts would need routing by organization like caches have by space), signing in with GitHub (needs the App's OAuth), a per-repository check of what a token may see.
  A bucket per organization (`storage`, `artifacts`, `caches`, `api`): `storage.Service` keeps an organization's bucket settings and keys sealed with the vault in the organization's scope under the name `$STORAGE` (the `$` cannot be in a secret's name) and the kind `storage`, so a workflow cannot name it (`ForRun` only takes the kinds secret and var), the secrets API cannot list, overwrite or delete it, and `PUT /v1/storage` tries the bucket with `storagecheck` first and refuses one that does not work. `For(org)` gives the organization's bucket, else the server's own (`Default`), and a version that changes with the settings. `caches.Config.S3For` and `artifacts.Config.S3For` take it: a cache space (`Space.Org`) is made again on the new bucket when the version changes (entries whose objects are not there are dropped at lookup), and `artifacts` routes each request to the service of its run's organization (the run in the token for the Twirp API, in the path for an upload; an organization's bucket gets a service of its own under the prefix `artifacts/`; an error in finding the bucket is a 500, never a quiet fall back to the server's disk). Without a master key all organizations use the server's own. The bucket path itself (S3) is checked only against fakes and a live refusal of a bucket that does not exist; nothing has run against a real bucket.
  Step 1 notes follow. It is written to be split into its own repository later (the user's decision, 2026-11-01: four repositories, frontend, backend, runner, cli, plus a library repository for what they share), so it imports only packages that would move to the library (`value`, `workflow`, `expr`, `trigger`, never `cmd/…` or `ghrunner`) and reaches the outside through small interfaces of its own. `store`: the `Store` interface and its SQLite implementation (pure Go `modernc.org/sqlite`; numbered SQL migrations embedded in `migrations/`, applied at open, a database from a newer server is refused; times are unix milliseconds); events are keyed by GitHub's delivery id, runs are unique per event and workflow file, both inserts are `ON CONFLICT DO NOTHING` so repeating is harmless. `github`: reads workflow files and changed files with a `TokenSource` (`App`: JWT signed with the App's key traded for an installation token and cached until a minute before it expires; `StaticToken` for development). `intake`: the webhook `Handler`. It checks `X-Hub-Signature-256` (constant time, an empty secret refuses everything) before looking at the body, answers pings, drops events it does not handle and repositories not in `Allow` without storing them, stores the delivery as `received`, answers 202, and in the background reads the workflows at the event's commit, calls `trigger.Match` for each (changed files from the compare API; unknown, as for a new branch, means path filters do not block) and creates a queued run per match, keeping the workflow text. The delivery's `note` says per file `run`, `skipped` or `invalid`. `Recover` handles deliveries a restart left `received`. A pull request from another repository, or whose fork was deleted, is marked `Fork`. `api`: read-only JSON, `/v1/runs`, `/v1/runs/{id}`, `/v1/events/{id}` behind a bearer token (503 while none is configured; compared by hash), `/healthz`, and `/v1/openapi.yaml` (embedded; keep it in step). `config`: secrets from env or `NAME_FILE`, refusing a file others can read. Verified with a signed replay of a real `cli/cli` push through the Cloudflare tunnel: the three runs GitHub itself ran for that commit. Not tried: a delivery from GitHub itself, a real pull request, App authentication against real GitHub.

- `internal/server/catalogsync`: keeps the catalog feed in the database. `Syncer.Sync` pulls `-catalog-url` (verified against `-catalog-key`, one or several ed25519 public keys, any one that verifies; with neither flag the library's `DefaultFeedURL` and `TrustedKeys` apply) at start and every `-catalog-interval` (24h, 0 = never), and stores the verified text in the `documents` table under `catalog-feed` only when it differs; a feed that cannot be pulled or does not verify leaves the stored one. `Executor.Catalog` plans runs with the built-in catalog with the stored feed laid over it (an error falls back to the built-in one), and the verified text travels with each job in `InstanceSpec.Catalog` as a **string** (the feed is YAML, not valid JSON; the protocol version is unchanged, an older machine ignores the field) for the machine to verify and overlay. The catalog only *names* things (strict character sets, no commands or URLs), which is why it is safe to store and send. Tests use httptest, no network.
- `internal/server/retention`: the `Janitor` that, at start and then hourly, purges the logs of finished runs past `-log-retention-days` (see Log retention above) and deletes expired API tokens (`Store.PurgeExpiredTokens`, a day after they expire). Artifact expiry (`artifacts.Sweep`) and the cache sweep (`caches.Sweep`, every 15 minutes) are separate sweeps described above.
- Metrics: `GET /metrics` (`api/metrics.go`, `Store.RunStats`), Prometheus text format, admin bearer token. `raccoonci_check{check}` (the same checks as `/readyz`, 1/0; the reason goes to the log, not to the output), `raccoonci_runs{status,conclusion}`, `raccoonci_oldest_queued_run_age_seconds` (0 when nothing waits: alert on it when no executor takes runs) and `raccoonci_build_info{version}`. Label values are escaped as the format requires. Executor-internal numbers (machines running, start waits, job durations) are not exported yet. `/healthz` is liveness, `/readyz` says whether the database accepts a write and the disk has room.
- SQLite transactions and `_txlock=immediate` (`store/sqlite.go`, `store/txlock_test.go`): `OpenSQLite` adds `_txlock=immediate` to the DSN because every `BeginTx` in the store is a write transaction. With the default DEFERRED transaction a read followed by a write fails in WAL mode with `SQLITE_BUSY_SNAPSHOT` (`database is locked (517)`) when another connection committed in between, and `busy_timeout` does not retry that error; an immediate transaction takes the write lock at its start and waits for it. This once made `Executor.Run` (via `RequeueInterrupted`) return at start, so queued runs were never taken while the process and its health check stayed up. Two more layers: `Executor.Run` tries the dealing with leftover runs 5 times (`startTries`, delay from `Executor.StartRetry`, 200 ms, doubling, stops when the context ends), and if the executor still cannot start, `cmd/raccoonci-server` logs it and shuts down gracefully with a non-zero exit so systemd or Docker restarts it. Never open the database with a DSN without `_txlock=immediate`; a new transaction that only reads should use plain queries, not `BeginTx`.
